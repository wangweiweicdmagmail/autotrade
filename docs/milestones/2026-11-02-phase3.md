# 第三阶段：本地事务账本与故障恢复

日期：2026-11-02。承接[第二阶段](2026-11-02-phase2.md)。按用户确认，本阶段聚焦个人使用的可靠性，
不包含安装交付、跨平台适配、依赖锁定，也不包含已暂缓的浏览器壳改造。
这是工作区交付记录，没有创建提交或标签，没有运行生产迁移或重启实盘。

## 1. 本地执行账本

新增 `execution/state_store.py`，只使用 Python 标准库 SQLite。
以原状态路径 `lots_state.json` 为例，权威文件为同目录的 `lots_state.sqlite3`：

| 内容 | 存储与保证 |
|---|---|
| 版本 | `PRAGMA user_version=1`，快照内含 `schema_version=1` |
| 订单与交易组 | 一份完整快照，在同一个事务写入；包含新增受理意图 |
| 校验 | SQLite `quick_check`、快照 SHA-256、订单身份与数量检查 |
| 写入顺序 | `BEGIN IMMEDIATE`、修订号核对、`synchronous=FULL`、提交或回滚 |
| 历史归档 | 终态快照与归档在同一事务写入，以订单和关闭时间去重 |
| 并发保护 | 沿用写进程锁，并以修订号拒绝陈旧快照覆盖 |
| JSON | 提交后原子导出，文件与目录执行 fsync；不再是权威状态 |

每次保存同时包含订单与交易组当前状态，但不跨执行引擎的异步调用持有数据库事务。
券商调用不在 SQLite 事务内；本地与券商之间没有分布式原子性。

## 2. 迁移、备份与损坏处理

1. 构造订单管理器只读加载，不执行迁移；生产取得写进程锁后重新加载并初始化账本，再连接券商。
2. 首次保存导入旧订单、交易组及 `trades-YYYYMMDD.json` 历史归档，整个数据库初始化在事务内完成。
3. 迁移前将原 JSON 保存为 `.json.pre-v1.bak`，已有备份不覆盖。
4. 迁移中断且无已提交数据库时，可重新从完整旧状态迁移；已有权威数据库时始终以数据库为准。
   大事务中断留下待回滚日志时，加载阶段明确标记“未加载、等待恢复”；取得写锁后由 SQLite 恢复，期间禁止保存或入场。
5. 损坏、摘要不符、重复订单身份、非法数量或未知版本会阻止加载，不能继续以空账本运行。
6. 只有 JSON 导出而权威数据库丢失时禁止回退；已有历史记录或迁移备份却无当前账本，也不能当成新账户。

迁移备份只保存升级前的旧 JSON，不是持续备份，也不包含升级后新增交易。
不能删除数据库、覆盖当前状态或恢复旧 JSON 来消除告警。
退回旧版本代码前须先处理存储兼容，不能让旧 JSON 写入者与新账本并行。

## 3. 持久化受理意图与恢复

### 入场

创建本地订单批次并保存 `entry_submission_pending` 后，才调用券商。
持久化失败不会提交入场；券商异常、任务取消或进程退出导致结果不明时保留意图。
券商返回明确订单号后保存身份并解除该受理意图。

实盘网关的限价括号、市价括号和 OCA 入场腿写入精确引用：

```text
autotrade:<lot_id>:entry
autotrade:<lot_id>:stop
autotrade:<lot_id>:breakout
```

重启后按精确引用和标的，在可见订单及当日成交中认回订单号，再进入已有成交/保护恢复流程。
同一引用对应多个订单时保持暂停；无匹配不等于没有提交，不会猜测取消或自动重发。

### 全量退出

先持久化 `CLOSING`，再撤保护；在平仓请求前保存委托数量及唯一的 `close_submission_ref`。
迟到或重启后可按该引用认回订单，继续累计成交核对。
缺少可归因订单或成交时继续等待，不重复发平仓单。

### 部分退出

在收缩保护数量前保存 `partial_exit`（委托数量和唯一引用）。
未核对完成时禁止再次部分退出或叠加全量平仓；失败返回不直接视为无成交。
重启后认回可见订单，按终态实际成交记账一次；真实均价未知时继续等待，不用现价或入场价替代。
记账和清理部分退出意图先持久化，再恢复剩余保护数量。
部分成交后撤单或完全未成交的撤单，会按实际剩余数量重新校准保护，修复原流程中缩量保护遗留的问题。

部分退出订单跨会话不可见时，即使查到订单号也可能无法确认剩余委托终态，继续保持暂停，需人工核查。

## 4. 运行时保护与界面

- 实盘重启后的开放订单须先完成对账，才允许新入场。
- 实盘券商断线时拒绝新入场，不转为虚拟成交。
- 持久化失败、未知受理、未完成部分退出、无法确认保护等问题暂停新入场。
- 撤单和退出仍按真实订单状态与原有安全条件处理；不会因一个新入场闸门整体禁用保护操作。
- 同一订单上的部分退出未知时，不能用全量退出绕过数量核对。
- 对账异常及逐订单恢复错误进入状态快照；周期对账可重试，恢复成功后重新计算问题。
- 顶栏仅在有问题时显示可展开的恢复/对账提示，不新增占用执行监控高度的常驻面板。
- 提示包括受影响订单、原因、最近核对时间、账本版本及修订号；净持仓差异只展示，不自动归因到交易组。
- SQLite 已提交但 JSON 导出失败单独展示；复盘读取权威归档。后续保存重试未完成导出。

## 5. 故障注入验证

新增 `tests/test_phase3_recovery.py`，全部使用临时目录、内存券商桩或隔离子进程。

| 场景 | 核对结果 |
|---|---|
| 旧 JSON 升级 | 备份保留，订单/交易组/归档能加载，重复归档不重复计量 |
| 损坏与未知版本 | 阻止启动，不回退为空账本 |
| 事务提交前实际退出子进程 | 保留上一份完整快照；首次迁移中断后可重试 |
| 大事务写入中实际退出子进程 | 待回滚日志保留到取得写锁后恢复，不在只读构造阶段修改 |
| 已提交但导出前实际退出子进程 | 重启读取已提交新状态，不用旧 JSON 覆盖 |
| 归档写入失败与再次保存 | 状态和归档共同回滚，重试后共同提交 |
| 陈旧写入者 | 修订号冲突，无法覆盖新状态 |
| 入场前存储失败 | 券商调用次数为零，后续入场被拦截 |
| 入场提交任务被取消 | 重启保留未知意图，不推断为已撤单 |
| 引用认回和重复对账 | 订单身份不变，不重复建仓或退出 |
| 部分退出成交后重启 | 只核对一次；部分成交撤单后的保护数量恢复 |
| 部分退出均价未知 | 保留意图，不猜价，不叠加退出 |
| 券商快照失败与恢复 | 问题可见，完整快照返回后重新核对 |
| 网关括号与 OCA | 真实网关方法在内存 IB 桩上为每条腿设置正确引用 |

## 6. 个人使用时的处理边界

出现恢复提示时先核对对应订单、券商成交与保护状态，让周期对账尝试认回。
查不到受理结果、引用冲突或历史超出券商查询范围时，需要人工查证，系统没有绕过事实核对的解除按钮。
账本损坏时保留 SQLite、可能存在的 journal、JSON 与迁移备份，先停止写入再诊断；不能用旧文件覆盖当前券商事实。

本阶段不保证所有故障都能无人值守恢复。旧模型接口、执行配置和兼容标识保留，
历史 PositionManager、独立跟单及所有遗留券商分支没有全面重写。
Pine 决策及历史 OHLC 回测的能力边界保持不变。
