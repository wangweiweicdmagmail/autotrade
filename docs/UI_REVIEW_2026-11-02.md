# 交易运维控制台界面评审

评审日期：2026-11-02。依据当前 `console/static/index.html`、`app.js`、`style.css`、相应控制服务，以及本轮开发中已检查的隔离预览。未操作生产交易界面或改变交易配置。

本报告保留评审时的问题与建议。后续已批准并实施的改动及验收记录见 [界面优化交付记录](UI_OPTIMIZATION_DELIVERY_2026-11-02.md)。问题分为现有代码能确认的语义问题，以及需要通过不同窗口尺寸进一步验证的体验问题；不把布局建议当作执行故障。

## 产品任务与结论

用户先在 TradingView 观察行情，再手动启动执行实例。控制台的首要任务是让用户确认启动对象、参数和启动状态，随后监控订单、保护与异常，并能明确地暂停或退出。
回测用于核对人工选择启动时机后，策略模型与执行模型的行为和结果。新闻、报告、研究和系统说明辅助这一流程。

现有多模型入口、实例归属、风险明细、恢复提示、一键回测和独立架构说明页值得保留。主要优化方向是信息分层、操作范围、参数生效语义和多模型一致性。

优先级含义：P1 为可能影响交易操作理解的问题；P2 为明显降低可读性或效率的问题；P3 为体验完善。当前没有仅据静态评审即可认定的 P0 界面故障。

## 1. 停止与平仓的范围不够清楚（P1）

**问题与依据：** 顶部启动表单选择一个策略模型和执行实例，但相邻“停止并全平”调用的是全局停止，后端遍历所有引擎和执行实例。逐行“停止加仓”调用 `stop_symbol`，还会停止尚未建仓实例的新入场。整组平仓确认仅显示标的，无法区分同标的下的不同模型和实例。已有平仓确认应保留，但需要补齐作用对象。

**建议：**

- 按钮区分“暂停此实例新入场”“退出此交易组”“暂停全部执行实例”“退出全部自动执行交易组”。最终名称需与后端实际处理的挂单和持仓范围一致。
- 全局操作放入单独的“全局控制”区域，不紧贴单实例启动选择器。
- 平仓确认展示策略模型、执行实例、标的、影响的挂单/持仓，以及当前数量；将撤单中、退出中与已完成分别反馈。
- 暂停操作说明已有挂单如何处理、保护与退出是否继续；不能只写“已停止”。文案以实际服务行为为准。

**验收：** 同标的运行两个模型时，用户无需猜测就能识别受影响的对象；请求提交成功不会被显示为已成交或已全部平仓。

## 2. 参数名称、作用范围与生效时点混在一起（P1）

**问题与依据：** 顶栏“单笔资金 $”实际被用于风险预算，容易理解成订单金额；“最大仓位”没有单位。止损 ATR 倍数与 Pine 策略模型入口共处顶栏，容易让用户认为它必然决定所有模型的初始止损。部分参数修改立即保存，部分只在启动或下单时提交。

**建议：**

- “单笔资金”按场景明确为“首仓风险预算（美元）”或“本单风险预算（美元）”；“最大仓位”注明账户净值百分比及实际限制范围。
- 参数放到其所属区域：账户风险、执行配置、手动下单、通知设置分别管理。
- 每个参数标明“账户级 / 执行实例级 / 当前订单”和“立即生效 / 下次启动生效 / 仅新订单生效”。具体范围由实现核实，不统一猜测。
- Pine 初始止损明确显示“来源：策略模型”；ATR 设置在相关手动或历史流程中显示，避免暗示它覆盖所有策略输出。
- 即时保存与待提交配置使用明确的反馈；编辑值与当前有效值分别展示。

**验收：** 用户修改一个参数前能知道影响哪些实例或订单，修改后能确认服务端实际接受的值。

## 3. 多模型界面仍残留金字塔专属含义（P1）

**问题与依据：** 实例风险条固定显示“累计建仓 /3”，第二仓 MFE 门槛固定显示 1R，保本说明引用全局 `pyramidAutoBreakeven`。这些文案对后续 `single_entry` 模型不一定成立。`WATCHING/ACTIVE/DONE` 等内部状态直接展示，也难以说明是否暂停、恢复待核验或退出中。

**建议：**

- 依据实例实际执行配置展示建仓上限、加仓条件和保本状态，不依据当前表单或全局 EMA9 开关推断。
- 基础状态使用“等待信号、委托中、持仓中、退出中、已结束”等业务名称；另列“新入场已暂停、恢复待核验”等限制状态。
- 单次建仓配置不显示加仓解锁和第二仓 MFE 提示；金字塔配置显示实际生效门槛。
- 后端没有提供的生效参数或订单确认状态显示“未提供 / 待核验”，不能由价格存在或默认值推断。

**验收：** 使用第二模型测试夹具检查页面，不出现未经配置的“3次建仓、2R解锁、3R保本”承诺。

## 4. 页面空间没有围绕当前任务分配（P2）

**问题与依据：** 自动执行主区始终占据上部，回测、研究、订单与运维等 12 个 Tab 共用底部面板。虽然已有高度拖拽手柄，但无执行实例时上方仍可能留有较大空白，回测结果需要在局部区域内滚动。1280×720 隔离预览可见这一空间竞争。

**建议：** 将主导航按任务分为四个工作区，保留统一环境和风险状态栏：

| 工作区 | 默认内容 |
|---|---|
| 执行监控 | 启动执行实例、实例列表、交易组、订单、异常 |
| 回测验证 | 独立参数、一键回测、输出与执行结果核对 |
| 研究复盘 | 选股、FVG、新闻、报告、影子记录、绩效与收益对比 |
| 系统运维 | 连接、盘前检查、运行日志、事件、跟单管理入口、系统架构 |

导航分组只是入口调整，不改变跟单等功能的实际服务边界。第一步可保留现有 Tab，只增加“展开工作区”功能并保存各工作区的布局；之后再调整主导航。

**验收：** 回测可使用主内容区；空实例列表不挤占当前任务空间；切换页面不丢失未提交参数和已完成结果。

## 5. 监控与操作的视觉权重倒置（P2）

**问题与依据：** 订单表左侧固定操作列宽 480px，先看到多个按钮，再看到标的、状态和价格。实例主表也是操作在前，且九列包含多行说明。窄窗口下关键指标可用宽度进一步减少。

**建议：**

- 默认列顺序为“标的与归属 → 状态 → 方向/数量 → 成交均价 → 保护止损 → 盈亏/风险 → 操作”。
- 保留一个常用主操作，其他放入有文字标签的菜单或详情抽屉；退出操作与普通详情分开。
- 实例首行只保留当前判断必要的信息，风险明细、MFE、恢复记录等展开查看；恢复阻塞和保护异常仍在首行可见。
- 账户净持仓与交易组持仓分开命名，同标的多个模型不能合并丢失归属。

**验收：** 1366×768 窗口默认可见标的、状态、数量、止损和盈亏，操作区不会占据接近半个内容宽度。

## 6. “系统正常”缺少可解释的层次（P1）

**问题与依据：** 顶栏已显示模式、IBKR连接、行情状态、风险和延时，恢复条也显示部分阻塞原因，但用户仍需要横向拼接信息，才能判断某实例为什么没有动作。仅有止损价格也不能证明券商保护单已确认有效。

**建议：**

- 顶栏优先保留“实盘/模拟、交易账户、券商连接、行情新鲜度、账户风险”；明细时钟和最大延时展开查看。
- 实例显示具体等待或阻塞原因，并附最近一次输入和决策时间，例如“等待有效信号”“新入场暂停”“恢复资料缺失”。
- 区分“策略止损价、待提交保护单、券商已确认保护单”；后两项需要真实订单状态支持。
- 异常优先呈现持仓保护、退出失败、数据陈旧等需要处理的事项，说明对象、影响和可采取的操作。新增规则前先核实后端能提供的事实。

**验收：** 用户能迅速回答“哪些实例正在运行、哪些被阻塞、是否有未确认保护的持仓”，且信息来源可追查。

## 7. 启动流程未突出人工择时这一真实工作方式（P2）

**问题与依据：** 当前“启动全自动”表述容易掩盖用户先观察行情、再主动启动实例的过程。界面尚未集中展示本次启动的有效参数与方向来源。

**建议：**

- 主按钮改为“启动执行实例”。启动区域包含策略模型、实例名称、标的、执行配置和风险预算。
- 启动时展示简短有效参数摘要；日常启动保持简洁，重大范围变化再要求针对性确认，不增加重复确认。
- 启动后显示真实启动时间、方向锁定状态及其来源、使用的参数版本。元数据缺失时需补充后端记录，不能靠浏览器时间代替。
- 多标的分别显示启动成功和跳过原因，保留当前已有的原因反馈。
- 手动下单入口使用“手动交易”，取代只有闪电图标的入口。

**验收：** 实盘启动记录与回测人工启动条件可对照；页面刷新后仍能看到真实启动信息。

## 8. 演示数据的作用范围容易被误认为全局模拟（P1）

**问题与依据：** `demoMode` 主要替换自动实例和订单演示数据，并在部分自动控制中阻止操作。页面顶栏仍保留其他配置编辑入口，不能把这个局部演示状态理解为整个系统均已隔离。

**建议：** 将它明确命名为“实例界面演示”，在该区域持续显示演示标识。需要全系统演示时，应使用独立的模拟环境与模拟数据源，不能仅靠前端开关实现。LIVE、DRY-RUN、历史回测和局部演示分别命名。

**验收：** 用户不会因为看到局部演示数据，就认为其他真实配置或交易入口已自动失效。

## 9. 字号、颜色和布局需要统一可读性标准（P2）

**问题与依据：** 多处关键归属和状态说明使用 10–11px 字号、低对比灰色；同一行红绿颜色可能分别表示方向或盈亏。部分弹窗使用固定宽度，实例表隐藏横向溢出。

**建议：**

- 核心数据使用 14–16px，常规表格与说明以 12–14px 为主；风险、归属、恢复等重要说明不使用极小字。
- 所有状态配合文字，方向与盈亏分列，颜色不能单独承担含义。
- 金额、股数、R值与百分比保留单位并统一精度；小额盈亏不要被整数金额格式化隐藏。
- 键盘焦点清晰可见，图标入口有名称，禁用原因能通过文字获得；文案与背景对比需实测。
- 窄窗口优先折叠非关键列，必须横向滚动时提供可见滚动区域；弹窗使用视口约束。

**验收：** 至少检查 1920×1080、1366×768 和窄窗口布局。当前没有完成全套尺寸与无障碍测试，不宣称已达标。

## 10. 回测结果需要更便于形成可复核的验证结论（P2/P3）

**问题与依据：** 一键回测、人工启动时间、参数快照、输出校验、决策与订单明细已经加入，应保留。进一步验证预期仍依赖人工在多块文本中对照，未保存的结果也不便后续比较。

**建议：**

- 主要阅读顺序为“本次条件 → 输出完整性 → 交易结果 → 策略信号 → 执行决策 → 订单”。
- 提供按时间和订单的联动定位；后续增加带信号、成交和止损标记的价格图。
- 允许导出运行参数、数据来源、时间假设和完整结果；若保存历史运行，记录模型声明与执行代码版本。
- 用户可记录“预期入场/退出及原因”并与结果对照。在没有预期基准时，只报告数值校验与执行事实，不自动标记策略验证通过。
- 保留零交易说明、模拟成本限制及启动时间近似说明，不增加单步操作。

**验收：** 同一组人工启动条件能复核差异；用户能够追溯盈亏来自哪些执行事件，而非仅凭收益判断策略正确。

## 推荐实施顺序

**第一轮：操作理解与语义。** 修正风险预算名称、停止/平仓范围、模型专属文案、状态名称、演示边界；补充实际生效参数和操作结果反馈。涉及保护确认等能力时先核实后端数据。

**第二轮：布局与导航。** 顶栏状态化，配置按作用范围归位；回测支持主工作区，订单表缩减操作占宽，实例详情展开。逐步调整，保留常用操作路径。

**第三轮：验证与追溯。** 图表联动、可导出的回测报告、启动记录和结果比较，补齐多尺寸和键盘操作验证。

界面重构期间不改动 Pine 信号含义、执行配置语义、既有订单归属和实盘风控。修改前后使用同一组模拟实例、异常和订单数据核对显示；确认界面动作仍调用正确的作用对象。
