# Agent 交易研究数据系统设计

日期：2026-11-23。状态：长期研究约定与目标设计。M1和M2已经实现，当前命令、数据边界及隔离验证见[M1与M2使用说明](AGENT_TRADING_RESEARCH_M1_M2.md)；M3和M4仍为目标能力。原有按秒审计保持不变，见[实盘审计](LIVE_AUDIT.md)。

具体模块改动、M1至M4交付范围、接口草案和验收用例见[开发方案](AGENT_TRADING_RESEARCH_PLAN.md)。

## 交易目标与研究职责

用户的交易目标是跟随NAS100、SPX500的方向和节奏，选择趋势质量较好的个股，及早参与趋势启动和回调后的延展。前十候选榜缩小观察范围，具体入场仍要结合大盘与个股位置。长期目标是在同等风险、成本和可交易机会口径下，使系统的独立交易决策取得优于用户人工交易的结果。

Agent负责每日订单复盘、向用户核实每个不明确动作的思考、提炼可检验的交易规则、优化候选与指标算法，并记录每轮验证。经验保存在项目的数据与研究记录中，不依赖某一段聊天的上下文记忆。自动研究职责不等于当前已获准自主实盘交易；新规则启用和自动交易范围仍由用户明确确认。

超过100笔完整交易后进行第一次系统评估。统计以交易组的完整开平仓过程为主，分批成交或同组减仓不重复算作独立样本；部分结束和归属不清的记录另列。达到数量本身不代表已掌握方法或已经优于人工，应继续使用未参与规则提炼的新交易验证。

## 最小长期保存集合

保存能够重算的行情底稿，以及无法通过价格重建的决策和交易事实。全股票池指标不逐秒重复长期归档，批量计算结果作为可失效的临时缓存。

| 数据集合 | 最小内容 | 保存时机与用途 |
|---|---|---|
| 行情底稿 | TV原始1m、5m OHLCV；数据源、请求及解析标的、周期、时段、复权和K线时间；少量日线与会话锚点 | 已确认K线持续归档；启动、重连及盘后检查补齐；供本地指标重算 |
| 当时榜单 | 确认时刻、前十名次、方向、得分与分项、评分版本、股票池版本、覆盖率及未就绪原因 | 每个接受的完整收盘分钟批次追加一次；区分无候选与数据未齐 |
| 订单与动作 | 本地批次及交易组身份、券商账户与订单身份、申请、准入、受理、成交、撤改、减仓、保本、退出及原因 | 每个动作或回报发生时追加；执行账本和券商回报保持原权威关系 |
| 方法与研究记录 | 用户对动作的解释、经确认规则、待解问题、源码及参数版本、实验假设、结果和结论 | 用户解释、规则修订或实验运行时保存；供后续Agent继续工作 |

保留日线或等价参考数据，是因为进攻区域、昨日高低点及指数会话锚点依赖这些输入。1m与5m各保存原始序列；当前不以自行聚合结果替代TV五分钟输入。股票extended与指数default分别记录，沿用[统一预热约定](EXTENDED_INDICATOR_WARMUP.md)。

行情存储按数据源、解析标的、周期、时段、复权和开盘时间区分序列。记录实际接收时间；历史修订保留旧版本或可恢复的差异。事后补齐的数据标明补取时间，不冒充实盘当时已经收到。

订单关键决策附精简证据：关联K线版本、当时已接受榜单、观察价、实际使用的指标及止损、实时或确认状态、判断与接收时间、策略和执行配置版本。保护及退出仅保留相关批次证据，不复制全股票池指标。

一分钟OHLCV足以支持分钟级研究，但不能还原每一次根内价格变化。关键实时决策保留当时的局部K线与实际指标值；历史OHLC中的先触止损或先触入场不确定时，应输出歧义或不同成交假设的结果，不编造逐笔路径。

## 完整性与版本清单

每个美东交易日生成数据清单，包含当日股票池、数据源与时段、可查询时间范围、各周期覆盖、实际预热起点、日线输入、缺口与补取结果、数据修订版本。按交易日历和数据源会话检查，不能把普通交易日根数套到提前收市或指数全天序列。

无成交、停牌、授权问题与订阅断流分别记录；无法确认原因时标为待核实。不能用前价填充缺失K线后声明数据完整。数据不满足预热或时间对齐要求时，研究结果标为受限；先列缺口，再决定可研究的日期与标的。

可复现记录同时固定：

- Pine源码实际内容和哈希、输入参数、plot映射、PineTS及适配器版本。
- 候选评分、准入、持仓保护、执行规则的代码或内容版本，以及运行时实际配置。
- 股票池、时段、复权、时区、最小价格跳动、数据修订和实际预热范围。
- 成交、滑点、手续费和根内事件顺序的模拟假设。

仅保留代码提交号不足以重现未提交草稿或被覆盖的参数。相同实验使用固定输入；源码或数据变化后生成新实验，保留旧结果。

## 每笔交易的学习记录

每日逐单覆盖开仓思考、持仓中的动作及平仓思考。先建立事实时间线，再整理用户解释，最后提出可检验的规则。

| 部分 | Agent应核对的内容 |
|---|---|
| 开仓 | 为什么选这只、为什么是此方向和时刻；当时大盘节奏、个股趋势阶段、候选名次、位置、初始止损与计划 |
| 持仓 | 加减仓、保本、止损修改和保护开关变化分别由谁触发；用户当时看到什么变化，想解决什么问题 |
| 平仓 | 是人工主动判断、保护成交、已授权自动规则、外部订单守卫还是异常处理；原因与原计划是否一致 |
| 结果 | 实际成交、费用、R、MFE、MAE、盈利回吐；哪些结果由选择、时机、退出或执行造成 |

外部订单守卫强平、系统故障、券商拒单与自动规则动作不能直接当作用户主动交易偏好。用户交易和系统动作分开归因；盈利不能单独证明决策正确，亏损也不能单独推翻一条规则。

任何动作的思考不明确，都要向用户询问。每个疑问绑定具体交易组、动作和时间，展示已知事实及相关行情片段，针对缺失原因发问。不得仅凭价格走势、备注推断用户心理，也不能把Agent推断写成用户确认的交易规则。

待问、已问、已回答和已确认分别记录。问题较多时按交易组分批询问，未回答项目保留在队列中，不因新一日复盘而遗漏；用户答复保留原意、来源和时间，后续修正保留历史。没有明确解释的动作不作为已标注训练样本，仍可纳入客观成交统计。

用户在本对话或后续对话回答具体交易问题时，处理答复的Agent同步更新对应问题与方法记录；不等下一次定时任务才保存。已问未答的问题保留原身份，不在每天重复创建。

可选的临场备注帮助减少事后回忆偏差，但不增加必填下单步骤。没有记录的主观原因，复盘中明确向用户核实。

## 交易方法的积累

每条方法记录适用的大盘状态、个股趋势阶段、入场触发、位置、初始止损、持仓管理、退出、失效条件及例外。规则绑定支持与反例交易、用户确认状态和版本，区分用户明确表达、Agent提出的假设和已验证结论。

例如，用户解释某笔空单来自大盘触及压力与个股提前转弱，应把这两个条件拆成可观察事实。随后比较同类成功、失败和未交易机会，检查规则覆盖情况；不能围绕一笔盈利交易不断补条件，使它成为唯一符合条件的样本。

方法提炼需要逐渐形成两类输出：可执行的确定性策略条件，以及目前仍依赖用户判断、需要进一步解释的情境。Agent能够说明每条建议依据了哪些已确认方法，以及哪些条件尚不确定。

## Agent查询与实验接口

提供固定的研究入口，供Agent先读摘要，再按需取片段。底层查询和数值运算在本地完成，避免把全股票池逐秒快照加载到对话。以下是拟建接口职责，不代表现有HTTP路由。

| 研究入口 | 输入与返回 |
|---|---|
| 数据清单 | 日期或日期范围；返回股票池、覆盖、缺口、时段和可用版本 |
| K线查询 | 序列、区间、周期和数据版本；返回有序OHLCV与质量状态 |
| 榜单查询 | 日期、确认时刻和版本；返回当时真实榜单及缺数状态 |
| 交易解释 | 交易组或批次；串联动作、成交、榜单、局部行情、用户解释及待问问题 |
| 指标与策略回放 | 固定数据、模型和参数版本、可见时间及成交假设；返回指标、信号、准入及模拟动作 |
| 实验比较 | 基线与候选实验；返回逐日、逐交易及逐趋势段差异、反例和受限项 |
| 方法与疑问查询 | 规则、交易组或日期；返回用户已确认方法、证据、未解原因和历史修订 |

所有时间查询区分K线开盘时间、收盘后可知时间与实际接收时间。一分钟收盘排名只能消费当时已收盘输入；五分钟指标也遵守各自确认边界。新算法在历史数据上的重算结果不能覆盖当时真实榜单。

研究读模型使用执行账本的只读投影，不在研究进程修改账本。模拟使用独立执行实例、SimBroker和临时状态路径；代码验证遵守项目隔离测试约定。当前Agent只读入口继续见[实盘审计接口](LIVE_AUDIT.md)。

## 每日研究流程

默认每天北京时间10:00进行一次订单复盘，覆盖上次检查以来尚未复盘的已结束交易及新动作。该时间覆盖前一美股交易日盘后结束；周末及休市日检查遗留问题和新答复，没有新增材料时不生成重复交易分析。计划由本机自动化调度，实际运行和数据可用性以任务结果为准。

研究输出使用独立的`logs/agent_research/`目录：`progress.json`保存已覆盖的交易和动作版本，`questions.jsonl`追加疑问与状态变化，`methods.jsonl`追加用户确认方法及版本，`reviews/`按复盘日期保存报告。它们是研究记录，不是执行账本；方法支持交易、回答来源和待核实项均可由后续Agent查询。

首次运行先复盘最近一个有真实成交的交易日，其他历史记录进入待复盘队列分批补充；不一次性扫描大型审计库。后续优先处理新动作和用户答复，再推进历史队列。

1. 读取项目约定、数据设计、已有交易方法、疑问队列与上次进度，查询数据覆盖。
2. 按精确订单及成交身份导入新增事实，处理跨日平仓、迟到回报和修订；不能用价格或数量相同认定同一成交。
3. 对每笔新增完整交易建立时间线，并检查已有持仓的新动作；区分人工、自动规则和异常处置。
4. 对每个不理解动作逐项提问并登记；先完成不依赖用户解释的事实分析，已回答部分再更新方法记录。
5. 输出每日复盘：逐笔开平仓思考、动作解释、实际结果、待问问题和可能值得验证的假设。
6. 对证据充分的问题建立独立实验，保存基线与候选版本、样本和结果；实盘规则保持用户已启用的版本。

复盘进度记录已覆盖的交易和动作版本，已看过的事件不重复建档；新增动作、修订或用户答复重新打开对应研究记录。自动任务不持续监控行情，不为了凑齐样本补造交易或重新发单。

## 优化与独立交易的评估

候选算法优先比较首次入榜延迟、趋势期间覆盖、漏掉的有效趋势段和反复进出榜。事后趋势标签只供评估，逐分钟排名仍只使用当时可见输入。

订单分析以初始实际成交与初始止损确定R基准，后续保本不改变分母。分别统计实际净结果、MFE、MAE、盈利回吐、滑点、费用及保护延迟，区分选择、入场和退出的贡献。历史假设交易与真实成交分开统计。

实验保存提出假设的原因、涉及交易、基线、改动、日期、结果和失败样本。规则提炼与评价日期按时间分开；同一交易日和同一市场行情下的多个订单不能都当作独立证据。记录每次尝试，避免只留下表现最好的版本。候选评分分数不解释为盈利概率。

第一次100笔评估应回答：用户已解释多少交易和动作、多少方法能够明确表达、还有哪些例外，规则在后续新交易上能否提前给出同类判断。独立交易能力分阶段验证：

| 阶段 | 需要取得的证据 |
|---|---|
| 方法理解 | 用户核对规则表述和交易归因；所有关键未知项明确列出 |
| 独立建议 | Agent在结果出现之前记录候选、入场、止损、管理和失效条件，之后再与人工选择比较 |
| 影子执行 | 用独立模拟验证持仓、风险、成交假设及异常处理，不复用实盘订单管理状态 |
| 有限自动执行 | 用户明确批准范围，已通过独立样本与影子验证，再启用对应软件执行配置 |

比较是否优于人工，应在相同可用信息、股票池、风险预算、成本和评价时段下，同时看净R、回撤、尾部亏损、交易次数、行情覆盖及执行稳定性。未成交建议也保留，不能只展示有利样本。超过100笔或单一回测的胜率不构成自动启用条件；自动化的范围和资金权限保持明确授权。

## 现有实现的衔接顺序

当前行情审计在[LiveMarketAudit](../engine/live_audit.py)按秒保存应用快照；[研究库](../research_db.py)保存五分钟历史与部分指标；[本地回测缓存](../engine/local_pine_history.py)按需保存EMA7数据和计算结果；[榜单读模型](../service/market_rhythm.js)覆盖写入最新文件；[事件服务](../console/services/events.py)追加交易事件，[执行账本](../execution/state_store.py)保存权威执行状态。

实施先后为：

1. 建立1m和5m确认K线持续归档、必要日线输入、数据版本与完整性清单。
2. 追加保存完整分钟榜单、关键订单决策证据与实际配置版本，贯通现有账本和事件。
3. 建立Agent查询、逐单问答、方法记录、每日进度与研究报告；已有数据不足时仍可先做受限的订单事实复盘。
4. 接入同源计算、完整准入与保护回放、实验比较，再评估缩减全池逐秒审计。

现有审计数据先保留。只有在迁移、数据覆盖及关键决策证据核对通过，并有备份和恢复验证后，才评估切换归档策略；删除旧库需要另行明确授权。不能为省空间先丢掉尚未提取的交易证据。

验收应支持在断网环境下，选择一个数据完整的交易日重算指标、读取当时榜单、还原每笔订单及已确认的用户解释，并输出固定基线与候选实验的差异。缺数据、未知思考和根内执行歧义要在结果中可见。
