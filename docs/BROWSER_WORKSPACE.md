# 启动时自动打开三个独立窗口

局域网客户端的 TradingView 图表在各自电脑上绑定和切换，安装和验收步骤见 [Chrome 扩展](../extensions/autotrade-tv/README.md)。

本机缺少完整 TV 凭据时，工作区准备后会打开独立登录页，加载页明确提示用户登录，后台自动保存会话后继续订阅；登录等待不会重复启动行情进程或占用行情诊断超时。见 [首次登录引导](TRADINGVIEW_LOGIN.md)。

当前默认使用三个独立窗口：`auto_trade` TV八格、`auto_trade2` TV六格、AutoTrade控制台。八格保留第3～10名映射；六格上排为席位1/NAS100/SPX500、下排为席位2/QQQ/NVDA；控制台左榜单右订单批次。详细接口和回读规则见[当前工作台说明](MARKET_RHYTHM.md#当前三窗口布局2026-11-20)。

`restart_live.sh`会在停止旧服务前检测可用的Python及项目依赖，避免GUI工具的PATH误选未安装uvicorn的Homebrew环境。可用`AUTOTRADE_PYTHON`指定解释器；`./restart_live.sh --check-python`只检查并打印解释器，不停止或启动服务。正式服务使用独立后台会话、关闭继承的标准输入，启动命令结束后继续运行；行情与连接的就绪检查沿用只读接口。

启动先等待HTTP可访问，再按确切URL复用已有页面，缺失页在新窗口打开；不会重新加载、关闭已有图表或覆盖订单草稿。普通重启会修复专用控制台与八格图表的target ID绑定。三个页面若已在各自窗口则直接复用；重复副本或同窗口恢复会给出明确提示，保留原页面，不阻止交易服务启动。设置 `CONSOLE_AUTO_OPEN_BROWSER=0` 禁止自动准备浏览器；`CONSOLE_AUTO_ARRANGE_WINDOWS=0` 跳过三窗口整理。旧 `CONSOLE_AUTO_SPLIT_BROWSER` 不再用于默认启动。

以下为旧原生左右分屏实现的历史说明与独立工具，默认启动不再调用。

## 启动与生效

照常启动 `./run_console.sh`；已有实盘启动方式也沿用应用启动流程。本轮修改了后端启动服务，因此需要在下次重启控制台后生效，单独刷新页面不会重新执行布局整理。本轮没有重启正在运行的交易服务。

应用先轮询控制台 `/api/startup`，确认 HTTP 已返回有效的加载状态后，才准备使用 `~/.tv-chrome-profile` 的专用 Chrome 与现有调试端口，避免服务尚未监听时打开控制台而显示“访问失败”。这里不等待 `ready=true`：行情、指标和券商的就绪进度仍由加载页显示，避免浏览器就绪条件形成循环等待。

首次启动时在同一新窗口中打开控制台和 TradingView；复用已有浏览器时补齐缺失页面。图表就绪后激活控制台，再通过原生菜单选择已有图表作为右侧视图，不重新加载图表或改变其标的、指标和图表配置。已有正确左右分屏直接复用；已分屏但顺序相反时尝试反转视图，上下布局尝试改为并排显示。

原生界面操作按调试端口对应的进程 PID 定位，使用 `controller/mac_workspace.py` 中的 macOS 可访问性 C API 句柄，不依赖 AppleScript 按名称解析进程。每次点击前再次核对控件 PID。只支持本机端点；无法唯一确定进程时停止整理。程序检查同一窗口内两个页面的位置，只有确认控制台在左、图表在右才记录分屏成功；两个不同窗口不会算作原生分屏。

## 权限与失败提示

点击股票时，主机通过 Chrome 的窗口 ID 定位发起点击的 AutoTrade 标签页。默认只切换同一窗口里的TradingView图表；可通过主机“绑定TV图表”明确绑定另一窗口，绑定只属于发起的AutoTrade标签页，图表变化后须重新绑定。同窗口有多个图表时使用唯一可见图表，无法确定时提示将目标图表与 AutoTrade 分屏。

当前TV使用两行四列八宫格。单标的联动继续使用视觉行优先第六格（下排第2列），其他七格只做读回核对。整体同步按第3～10名映射：上排9/7/5/3名，下排10/8/6/4名。单图最大化或布局不符会提示调整，不回退到第一格。主机后端需要重启加载，远程客户端需要更新扩展至0.6.0并刷新控制台；详见[四宫格与TV八宫格联动说明](MARKET_RHYTHM.md#控制台单标的切换固定第六格)。

首次使用可能需要在“系统设置 → 隐私与安全性 → 辅助功能”授权实际运行控制台的应用。程序不会自行更改系统权限，也不再依赖 System Events 自动化授权。分屏失败会在启动状态的“图表工作区”阶段和日志中说明原因；浏览器已经打开时，不会因桌面权限问题一直重试菜单操作或阻止交易服务就绪。

支持 Chrome 中文与英文菜单名称；本次在本机 Chrome 156 中文界面实际确认了原生菜单、选择已有标签页和反转视图命令。浏览器更新或其他语言可能改变菜单；程序会报告失败，不将普通双标签页当作分屏成功。控制台和图表若已被人为拆到不同窗口，本轮不关闭或重新加载已有图表，可能需要先移到同一个窗口后重试。

可以只重新整理浏览器，不重启交易服务：

```bash
python3 -m controller.browser_workspace
# 自定义控制台地址 / 调试端点时：
python3 -m controller.browser_workspace --console-url http://127.0.0.1:8000/ --endpoint http://localhost:9222
```

该独立命令不加载交易应用，不启动行情采集、执行实例或券商连接。

“正在准备交易工作区”加载页随分屏宽度伸缩，最多使用 900px 卡片；超过 640px 时检查项两列排列，窄窗口单列。状态详情和错误完整换行，短窗口可以纵向滚动。1020px、600px、360px 合成状态截图已检查，未出现横向溢出。

## 可选开关

| 环境变量 | 默认 | 行为 |
|---|---|---|
| `CONSOLE_AUTO_OPEN_BROWSER` | `1` | 自动打开并准备工作区；设为 `0` 时也不自动分屏 |
| `CONSOLE_AUTO_SPLIT_BROWSER` | `1` | 自动整理左右分屏；设为 `0` 时只保留标签页 |
| `CONSOLE_URL` | `http://127.0.0.1:8000/` | 控制台地址；使用非默认服务端口时相应设置 |

## 2026-11-02 重启无效果的修复

用户重启后，服务内存日志记录了“浏览器已打开，自动分屏未完成: ”，错误原因为空；启动状态因此只显示标签页就绪。这与原生整理的 30 秒超时异常文本为空相吻合。

原脚本使用整个窗口的 `entire contents`，会连 TradingView 的网页可访问性内容一起展开。已改为逐层检查浏览器框架，遇到网页 `AXWebArea` 即停止深入；仅对 Chrome 自己的轻量标签页选择器展开内容。这样避免为定位两个页面或菜单遍历整个图表 DOM。

进一步真实复验发现关键的同名进程问题：`set p to first application process whose unix id is 9138` 会得到按名称保存的 `application process Google Chrome` 引用；之后读取 `unix id of p` 实际返回日常 Chrome 的 PID 1040。仅在初次查询时按 PID 过滤，不能保证后续 AppleScript 界面操作仍然指向该进程。旧脚本已移除，改用 PID 创建的原生句柄，避免错误访问同名浏览器。

此外，Chrome 原生标签页选择器的静态文本在 `AXValue` 中，不能只读取 `AXTitle`。新的驱动只展开该选择器的内容，匹配已有图表候选，并验证同窗口内的位置；已有未完成的选择器也会复用，不再次创建分屏。

超时现在会终止并回收整理进程，返回明确的“超过 30 秒”说明；启动层也为任何空文本异常提供类型兜底，避免再次把分屏失败显示为普通标签页就绪。`-1719` 也不再被一律误判为权限不足。最终实际整理、重复运行与控制台解释器复验均已成功。

## 启动停在部分标的确认（2026-11-05）

启动48/53或49/53不一定是指标版本问题。此次根因为全股票池单行tick加入突破Pine上下文后超过4MB，`asyncio`读取报 `Separator is not found, and chunk exceed the limit` 后退出；尚未进入最后一批标的时快照就冻结。

采集器流上限现为16MB；历史OHLC仍完整保留，仅在美东09:40至10:30之前的历史行附带突破上下文，实时/确认根仍保留完整上下文。读循环退出由守护任务恢复，不依赖是否处于交易时段。单标的重建设置90秒期限，重建无回报不能因rebuilding标志永久跳过，核心确认趋势指标缺失也需恢复；可选盘前区间缺值不触发整图重建。

`/api/startup` 的 `market_pending` 列出未确认的标的，加载页直接展示；超过240秒会显示明确等待名单，不把已有48个全部正常误判为全体指标故障，也不降低53/53的就绪门槛。回归包含超过4MB的53标的合成快照、非交易时段读任务退出恢复及单标的重建超时，全部使用内存桩与临时目录。

## 连续陈旧与采集CPU满载（2026-11-05）

盘中曾出现内容停更45秒后重启，重新加载7个指标与分批订阅约需97秒，造成反复断档。采集进程CPU现场达到约100%。价格回调原先也会被纯study事件触发，并反复读取会排序的`chart.periods`、重建160根闭合历史。

当前采集器只在`$prices`事件处理价格，每次只读取一次periods。闭合历史以时间/OHLCV签名缓存，根内更新只刷新实时OHLC、ATR与既有兼容EMA；新K线、历史修正或新增预载历史会使缓存失效。Pine策略模型的EMA7、斜率仍直接读取原输出，没有改成Python或Node自算。

重连仍逐指标获取远端元数据核对版本；同版本正文缓存可直接使用，不再重复等待已知缺正文的translate重试。版本不一致仍重新获取或报缓存不匹配，不混合新元数据和旧正文。TradingView websocket连接、断开与错误现有明确日志，断开后退出行情子进程交给现有守护重连；行情陈旧阈值及执行保护未放宽。

本次现场验证：只重载行情子进程，控制台与交易服务保持运行。美东10:04:46左右完成53标的订阅后，持续观察至10:10:07，未再出现陈旧重启；10:05与10:10的新K线均正常到达。最后采样53/53确认、内容与传输年龄0.4秒、10:10新K线到达延时0.4秒；采集CPU由修复前约100%降至后续采样约1.5%～18%。单次观察不代表未来连接不会中断。Node回归27项通过，相关Python隔离回归46项通过；未放宽陈旧阈值或绕过执行保护。
